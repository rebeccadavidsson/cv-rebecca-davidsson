What is an AI software factory?

It’s the system around the coding agent, not the agent itself.

  • Work comes from a queue (backlog, Teams chat etc.)
  • Agents work in isolated environments.
  • Verification runs before a human ever sees the diff.

From scripts to a real factory

  • Guillermo Rauch: “The alpha is in your factory, not just the code.”
  • Stripe, Spotify, Shopify, Uber, Ramp all hit the same wall: too many PRs, not enough review.
  • They built queues, sandboxes, tool layers, verifiers, and merge policies before they built big fleets.

How the big players run their AI factories

Stripe – Minions

  • Intake: Slack message + emoji.
  • Isolation: Fast cloud dev boxes.
  • Tools: “Toolshed” with hundreds of tools.
  • Verification: Lint + tests, then CI.
  • Merge gate: Human review.

Shopify – River

  • Intake: @river in public Slack channels.
  • Isolation: Short‑lived harnesses.
  • Tools: Safe gateway to internal systems.
  • Verification: Auto PR review mode.
  • Merge gate: Human review.

Different tools, same idea: queue the work, isolate the agents, give them safe tools, verify first, then let humans decide what ships.

One factory or many?

  • Shared guardrails, shared MCP servers, less reinventing.
  • Or separate, local setups that are harder to control and harder to learn from?

Building: Guardrails or chaos

  • Agents need guardrails, not “good vibes”.
  • Otherwise they optimise the wrong thing.

Having guardrails not setup correctly

  • One company asked: “Close tickets fast.”
  • The agent deleted all open tickets.
  • Job done. Technically not wrong.

VLK Factory Police

  • Company‑wide rules for agents.
  • Central policies, shared checks.
  • “Police Agents” watching the “Normal Agents”.

Rule files for agents

  • Example: task = “fix warnings in this repo”.
  • Agent “fixes” them by deleting all lint rules.
  • You need written rules like “Do NOT delete lint rules”.

Do not EVER let them access credentials

  • Agents + secrets = horror story.
  • Never let them near credentials.
  • Seriously, just don’t.

Approval flows and limited tools

  • Add approval steps where it makes sense.
  • Give agents only the tools they actually need.
  • No “root access” for fun.

Approval is tricky

  • What if an intern sees: rm -rf *?
  • They might just click “Approve”.
  • We need guardrails that don’t rely on vibes.

Commit step: don’t overload the agent

  • Your implementer agent is already busy.
  • Making code compile is a full workout.
  • Don’t also cram all coding standards into it.

Separate the coding standards

  • Have a separate task: “clean up the diff”.
  • Let another agent enforce standards on the diff.
  • Implementation and polishing are different jobs.

Coding standards file

  • Put standards in CODING_STANDARDS.md.
  • Call that file from a separate agent run.
  • Don’t bury it in global instructions soup.

Testing: A factory that can’t verify output is useless

  • Our job is moving from writing code…
  • …to reading and testing code.

Make testing easier

  • Testing should be easy and fast.
  • If it’s painful, we won’t do it enough.
  • So we automate and visualise it.

Tree branching / multi‑variant

  • Use tools that show multiple options.
  • 4 screens, user picks the winner.
  • Track which one performs best over time.

Automation ≠ black box

  • Automating doesn’t mean losing transparency.
  • We still need a clear audit trail.
  • Factory should be fast AND understandable.

Review: do not skip humans

  • Skipping human review is a bad idea.
  • If there is an outage, who will understand the code to fix it?
  • So yes, humans still have jobs for now.

Code ownership matters

  • If production breaks, who do you call?
  • “The agent did it” is not a helpful answer.
  • Someone needs to own the code.

Agentic code reviews

  • Use agents to help with reviews.
  • Different model for coding vs reviewing.
  • One for security, one for quality, etc.

But watch the bill

  • Many review agents = many invoices.
  • Maybe start with two:
  • One general reviewer, one quality‑focused.

Default: commit, not comment

  • Comments create more work.
  • The goal of review is to finish the work.
  • So reviewers should commit fixes when possible.

Reduce comment noise

  • Have a team session on “less comment spam”.
  • Update linting and coding standards.
  • Let tools catch the boring stuff.

Improvement: Scrum for your agents

  • Agents also need retros.
  • Run a retro‑review skill on recent PRs.
  • Let it learn from feedback and comments.

Automate the learnings

  • Skill scans comments across PRs.
  • Finds patterns you can automate.
  • That’s real factory improvement.

Iterate weekly

  • Small changes, every week.
  • Factory gets better over time.
  • But first: just START!

Improvement routines

  • UI‑improvement agent.
  • Cleanup code agent.
  • Run them on a schedule, like factory cleaners.

Beware of doc rot: clean up your docs

  • Repos full of AI‑generated markdown.
  • Prune dead docs regularly.
  • Keep only useful and current ones.
  • Help agents find the good stuff fast.
